# R4: Supply-chain frameworks, signing, SBOMs, reproducibility, trusted publishing (state as of 2026-09-24)

Scope: releasing software from a git repository. All pages accessed 2026-09-24. Release dates are git tag timestamps fetched directly from each repository (`git fetch --depth=1 --filter=blob:none <repo> refs/tags/<tag>`), because GitHub page summaries returned wrong years in several cases. Quotes are verbatim and at most 40 words. `[Sn]` refers to the numbered source list at the end.

## 1. SLSA

- **Versions.** slsa.dev/spec serves v1.2 with "Status: Approved" and says "This is **Version 1.2** of the SLSA specification." v1.1 is labelled "Status: Retired" with the banner "Version 1.2 is the current version." A separate "Working Draft" exists. Spec stages are Draft, Candidate, Approved, Retired. [S1][S2][S3]
- **What's new in 1.2.** "Addition of the Source Track which helps organizations secure their source code development process and consumers establish trust in that source." [S4]
- **Build track (v1.2, build-requirements).**
  - Provenance exists, L1+: "The build process MUST generate provenance that unambiguously identifies the output package".
  - Provenance is authentic, L2+: "Consumers MUST be able to validate the authenticity of the provenance attestation".
  - Provenance is unforgeable, L3: "Provenance MUST be strongly resistant to forgery by tenants".
  - Hosted, L1+: "All build steps ran using a hosted build platform on shared or dedicated infrastructure".
  - Isolated, L3: "free of unintended external influence".
  - Distribute provenance, L1+: "The producer MUST distribute provenance to artifact consumers". [S5]
  - v1.1 level summaries: L0 "No requirements—L0 represents the lack of SLSA."; L1 "Package has provenance showing how it was built. Can be used to prevent mistakes but is trivial to bypass or forge."; L2 build platform must "Generate and sign the provenance itself"; L3 must "prevent secret material used to sign the provenance from being accessible to user-defined build steps". [S6]
- **Source track (v1.2).** L1 "Use a version control system." L2 "Preserve Change History and generate Source Provenance."; "The SCS MUST record all changes to Named References, including when they occurred, who made them, and the new Source Revision ID." L3 "Enforce organizational technical controls." L4 "Require code review."; "Changes in protected branches MUST be agreed to by two or more trusted persons prior to submission". Tags: "A Named Reference that is intended to be immutable. Once created, it is not moved to point to a different revision."; "If the SCS supports Tags, the SCS MUST be configured to prevent them from being moved or deleted." Example: "prevent the deletion of all `refs/tags/releases/*` using tag protection rules." VSA refs: "git references MUST be fully qualified (e.g. `refs/heads/main` or `refs/tags/v1.0`)". Consumer expectations "are tied to a _repository branch or tag_, whereas a VSA is tied to an _revision_." resourceUri form: `git+https://github.com/IntendedOrg/hello-world`. [S7][S8]
- **GitHub Actions hosted runners + artifact attestations.** GitHub docs: "Artifact attestations by itself provides SLSA v1.0 Build Level 2." and "Reusable workflows can provide isolation between the build process and the calling workflow, to meet SLSA v1.0 Build Level 3." Public repos: bundle "is also written to an immutable transparency log that is publicly readable"; private repos use GitHub's Sigstore instance which "does not have a transparency log and only federates with GitHub Actions". No statement from slsa.dev itself about GitHub was found. [S9]
- **slsa-github-generator.** README: "This project is **no longer actively maintained**. We are working on guidance and simpler tooling to replace it." It recommends GitHub artifact attestations. "They should not be assumed to receive updates, including for GitHub Actions runtime deprecations." Last release v2.1.0, tag 2025-02-24. Repo not archived. [S10]
- **slsa-verifier.** Latest v2.7.1 (tag 2025-06-25, published 2025-06-27). `verify-artifact` flags: `--provenance-path`, `--source-uri` (required), `--source-tag` (exact), `--source-versioned-tag` (semver match), `--source-branch`, `--builder-id`, `--print-provenance`. GitHub artifact attestation bundles (`.intoto.jsonl` / Sigstore bundle) are supported only through `slsa-verifier verify-github-attestation --attestation-path <file> --source-uri <repo> --builder-id <id> <artifact>`, "Currently limited to artifacts built with the following builder-ids": `github.com/bazel-contrib/.github/blob/master/.github/workflows/release_ruleset.yaml` and `github.com/bazel-contrib/publish-to-bcr/.github/workflows/publish.yaml`. Generic `actions/attest-build-provenance` output is not accepted. [S11]

## 5. Git signing, tags, release notes

- **Config (git master docs).**
  - `gpg.format`: "Specifies which key format to use when signing with `--gpg-sign`. Default is "openpgp". Other possible values are "x509", "ssh"."
  - `gpg.ssh.program`: default "ssh-keygen".
  - `gpg.ssh.defaultKeyCommand`: "run when user.signingkey is not set and a ssh signature is requested. On successful exit a valid ssh public key prefixed with `key::` is expected in the first line of its output."
  - `gpg.ssh.allowedSignersFile`: "A file containing ssh public keys which you are willing to trust. The file consists of one or more lines of principals followed by an ssh public key. e.g.: `user1@example.com,user2@example.com ssh-rsa AAAAX1...`"; "the trust level of a signature verification is set to `fully` when the public key is present in the allowedSignersFile. Otherwise the trust level is `undefined` and git verify-commit/tag will fail."; "Since OpenSSH 8.8 this file allows specifying a key lifetime using valid-after & valid-before options."; may live "in the repository itself using a path relative to the top-level of the working tree."
  - `gpg.ssh.revocationFile`: "Either a SSH KRL or a list of revoked public keys"; matching keys get trust level "never".
  - `gpg.minTrustLevel`: undefined, never, marginal, fully, ultimate.
  - `user.signingKey`: gpg key id passed to `--local-user`; for ssh, a private/public key file path, or a literal `key::ssh-ed25519 AAAA... identifier` (also `key::ssh-rsa`).
  - `tag.gpgSign`: "A boolean to specify whether all tags should be GPG signed."; "doesn't affect tag signing behavior enabled by `-u <keyid>`". `tag.forceSignAnnotated`: "whether annotated tags created should be GPG signed."
  - `push.followTags`: "If set to true, enable `--follow-tags` option by default." `push.gpgSign`: true / false / `if-asked`. [S58][S59][S60][S61]
- **SSH namespace and CI verification.** gpg-interface.c invokes `ssh-keygen -Y sign -n git` and `ssh-keygen -Y verify -n git` (also `-Y check-novalidate -n git`, `-Y find-principals`), and errors "gpg.ssh.allowedSignersFile needs to be configured and exist for ssh signature verification" and "ssh-keygen -Y find-principals/verify is needed for ssh signature verification (available in openssh version 8.2p1+)". Output line form: `Good "git" signature for PRINCIPAL with RSA key SHA256:FINGERPRINT`. CI recipe: commit an allowed_signers file (`release@example.com namespaces="git" ssh-ed25519 AAAA...`), run `git config gpg.ssh.allowedSignersFile <file>` and `git verify-tag <tag>` (or `git tag -v <tag>`), or call `ssh-keygen -Y verify -n git -f <allowed_signers> -I <principal> -s <sig>` directly. [S62]
- **git tag.** "A cryptographically signed tag object will be created when `-s` or `-u <key-id>` is used." "Otherwise, a tag reference that points directly at the given object (i.e., a lightweight tag) is created." "Annotated tags are meant for release while lightweight tags are meant for private or temporary object labels. For this reason, some git commands for naming objects (like `git describe`) will ignore lightweight tags by default." `-a` "Make an unsigned, annotated tag object"; `-s` "Make a cryptographically signed tag, using the default signing key" (backend from `gpg.format`); `-u <key-id>`; `-v`/`--verify` "Verify the cryptographic signature of the given tags."; `-m`/`-F` imply `-a`; "`--no-sign` overrides `tag.gpgSign`". Re-tagging: "The sane approach is to admit the mistake and use a different name". [S63]
- **git describe.** "By default (without `--all` or `--tags`) `git describe` only shows annotated tags."; `--tags` "use any tag found in `refs/tags` namespace"; "Annotated tags will always be preferred over lightweight tags, and tags with newer dates will always be preferred over tags with older dates."; output `v1.0.4-14-g2414721`; `--exact-match` = `--candidates=0`; `--dirty`, `--abbrev`, `--match`, `--exclude`, `--first-parent`. [S64]
- **git push.** `--follow-tags`: "push annotated tags in `refs/tags` that are missing from the remote but are pointing at commit-ish that are reachable from the refs being pushed." `--tags`, `--signed` (false/true/if-asked), `--atomic`. [S65]
- **git verify-tag.** `git verify-tag [-v | --verbose] [--format=<format>] [--raw] <tag>...`; "Validates the gpg signature created by `git tag` in the tag objects listed on the command line."; `--raw` prints raw status to stderr. The page is gpg-worded and does not mention SSH; SSH tags go through the same backend per the source above. [S66]

## 8. Reproducible builds

- **Definition.** "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts."; build-environment attributes include dependency versions, configuration flags and environment variables such as locale; "specified artifacts" exclude build logs. [S110]
- **Go.** Blog "Perfectly reproducible, verified Go toolchains" (2023-08-28): Go 1.21.0 is "the first Go toolchain with perfectly reproducible builds"; removed inputs: build path (`-trimpath`), cgo (disabled for toolchain), timestamps, host architecture, uid/gid in tars; `gorebuild` verifies posted binaries nightly at go.dev/rebuild; for user programs: `CGO_ENABLED=0 go build -trimpath`, cgo programs need a controlled C toolchain. cmd/go: `-trimpath` "remove all file system paths from the resulting executable. Instead of absolute file system paths, the recorded file names will begin either a module path@version (when using modules), or a plain import path"; `-buildvcs` "Whether to stamp binaries with version control information ("true", "false", or "auto"). By default ("auto"), version control information is stamped into a binary if the main package, the main module containing it, and the current directory are all in the same repository."; `GOFLAGS` "A space-separated list of -flag=value settings to apply to go commands by default"; `go version -m` prints embedded build settings. [S111][S112]
- **Nix.** `nix build --rebuild`: "Rebuild an already built package and compare the result to the existing store paths." `nix-store --realise --check` (manual for Nix 2.35.2): "This option allows you to check whether a derivation is deterministic. It rebuilds the specified derivation and checks whether the result is bitwise-identical with the existing outputs, printing an error if that's not the case."; with `-K` a differing output is kept at `/nix/store/name.check`. `nix store verify`: checks "its contents match the NAR hash recorded in the Nix database" and that it "is signed by at least one trusted signing key, is content-addressed, or is built locally"; options `--no-contents`, `--no-trust`, `--sigs-needed n`, `--substituter`; exit status is the sum of 1 (corrupted), 2 (untrusted), 4 (other error). reproducible.nixos.org: "you can use `nix-build '<nixpkgs>' -A hello --check --keep-failed` or `nix build nixpkgs#hello --rebuild --keep-failed`"; per-ISO reports (minimal/graphical, runtime/build-time) are linked at reproducibility.nixos.social jobsets 1, 2, 4, 5; no r13y.com mention on the page. [S113][S114][S115][S116]
